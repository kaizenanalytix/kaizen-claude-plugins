# raid-raci-setup

Creates **and keeps current** the **RAID Log (D33, Mandatory)** and the **RACI Chart (D34,
Mandatory)** for a Kaizen PDP engagement. The RAID Log is treated as a living governance document:

- **SETUP** — seeds a fresh RAID Log from the KT Brief and team list in `1. Sales Handoff &
  Transition/`.
- **UPDATE** — ingests new source material (emails, Teams transcripts, MoMs, or any PDP document)
  into an existing RAID Log, appending/amending without disturbing existing rows.

Outputs one or two `.xlsx` files in `7. Project Governance/`.

## When to use it

The Engagement Lead (EL) or Project Manager (PM) wants to stand up **or update** the RAID Log and
RACI Chart.

Trigger phrases:
- Setup: "set up RAID and RACI", "create RAID log", "generate RAID", "set up risk register",
  "RACI chart", "create RACI matrix", "generate RACI"
- Update: "update the RAID log", "add this to the RAID log", "update RAID from the latest
  email/MoM/meeting", "log these risks/actions/decisions", "refresh the RAID log"

## How it works

The RAID Log **must** be produced by copying and populating the bundled template — never by
building a workbook from scratch. The template is the single source of truth for structure,
formulas, dropdowns, formatting, and print areas; only data rows (from row 8) and header cells are
filled. It contains six sheets:

| Sheet | Purpose |
|---|---|
| Risks | Risk register (ID, dates, likelihood, impact, owner, strategy, mitigating/contingent actions) |
| Actions | Open items and follow-ups |
| Issues | Problems/blockers already occurring |
| Decisions | Key decisions made during sales that delivery must honour |
| Lookup | Dropdown source lists (Staff list in column A) |
| Instructions | Left untouched |

The **RACI Chart** has no bundled template and is built from scratch using the structure in the
SKILL.md (activities × team members with R/A/C/I cells). It is mandatory and generated by default
unless the user explicitly defers.

## How updates stay safe

All writes go through `scripts/update_raid_log.py` so the "don't clobber the log" rules live in one
tested place: it continues IDs per sheet, preserves formulas and header rows, appends the staff
list, dedups against what's already logged, and stamps every new row with a **provenance tag** in
its Notes column (e.g. `[Source: Email "Re: data access" 2026-07-10]`). Re-running the same source
adds nothing. Changes to *existing* rows are never silent — they're proposed for EL approval and
applied only via the script's `--updates` path. A `--dry-run` produces the EL preview before any
real write.

**Email scoping:** the skill never scans the whole mailbox. It asks for an Outlook category/tag
first, and falls back to a subject search if there's no category. See `references/source-ingestion.md`.

## Notes

- Populate the RAID template with `openpyxl.load_workbook` (default, keeps formulas). openpyxl drops
  the data-validation extension on save; dropdowns re-hydrate from the Lookup tab in Excel.
- Risk descriptions, dates, and names are copied verbatim from source documents (guardrail G3).
- Follows the shared guardrails (G1–G5) from the `guardrails` skill of shared-foundation-plugin —
  version-not-overwrite, confirmation gate before saving, and verbatim data handling.
- Dependencies: `openpyxl`; optionally an Outlook/M365 email connector and a Teams/meeting
  transcript connector (both degrade to user-supplied files if not authorized).
