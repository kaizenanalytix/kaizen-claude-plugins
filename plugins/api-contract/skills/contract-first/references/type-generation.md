# Type Generation

## What `scripts/generate_types.py` does

Given an `openapi.json`, the script walks every schema under
`components.schemas` and emits one TypeScript `.ts` file per schema into the
`--out` directory. Each file:

- Starts with a header comment: `// AUTO-GENERATED — do not edit`, plus the
  source file and generation timestamp, so anyone opening it in an editor
  immediately knows not to touch it and where to regenerate it from.
- Declares one `export interface <SchemaName> { ... }` (plus any nested
  interfaces referenced via `$ref` — the script generates those as their own
  files too, or inlines them if they're only referenced once, depending on
  how the schema is structured).

### OpenAPI → TypeScript type mapping

| OpenAPI                                   | TypeScript                          |
|--------------------------------------------|--------------------------------------|
| `string`                                   | `string`                             |
| `integer` / `number`                       | `number`                             |
| `boolean`                                  | `boolean`                            |
| `array` (`items: T`)                       | `T[]`                                |
| `object` / `$ref: '#/components/schemas/X'`| `X` (nested interface reference)     |
| `nullable: true`                           | `| null` appended to the field type  |
| field absent from `required`               | `?` appended to the field name       |
| `enum: [...]`                              | string literal union, e.g. `"a" | "b"` |
| unknown/unhandled schema type              | `unknown` (never silently wrong)     |

### Example

Given this schema:

```json
{
  "components": {
    "schemas": {
      "User": {
        "type": "object",
        "required": ["id", "email"],
        "properties": {
          "id": {"type": "integer"},
          "email": {"type": "string"},
          "display_name": {"type": "string", "nullable": true},
          "roles": {"type": "array", "items": {"type": "string"}},
          "team": {"$ref": "#/components/schemas/Team"}
        }
      }
    }
  }
}
```

`generate_types.py` produces `User.ts`:

```ts
// AUTO-GENERATED — do not edit. Source: openapi.json
// Regenerate with scripts/generate_types.py

import type { Team } from "./Team";

export interface User {
  id: number;
  email: string;
  display_name?: string | null;
  roles?: string[];
  team?: Team;
}
```

## How each side imports the generated output

**Frontend:** the `generated/types` directory is treated as a vendored
dependency — it lives in the frontend repo (or a small internal package the
frontend depends on) and is regenerated by CI whenever the backend's
`openapi.json` changes, then committed like any other file. Application code
imports normally:

```ts
import type { User } from "@/generated/types/User";
```

Nothing in `src/` outside `generated/` should describe a backend shape by
hand — if a type is missing, that's a sign the OpenAPI schema needs a new
`components.schemas` entry, not a hand-written interface.

**Backend (federation case):** if this backend needs to consume types
produced by *another* service's OpenAPI schema (e.g. a shared internal
platform service), run the same generation step but target Pydantic-style
models instead of TS interfaces (a `--lang pydantic` style extension of the
same script, or a sibling script following the identical mapping table).
Those generated models are imported the same way — treated as vendored,
never hand-edited, regenerated on schema bump.

## Why regeneration must be automatic, not manual

If a developer manually edits a generated `.ts` file to unblock themselves,
the next regeneration silently reverts their fix and the contract diff gate
won't catch it (the generator will just reproduce the same "wrong" type from
the schema). The only correct fix path is: change the OpenAPI schema (or the
backend model that produces it) → regenerate → commit both the schema and
the regenerated types in the same PR.
