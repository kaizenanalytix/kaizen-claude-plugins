# Alembic migration conventions

Choosing Alembic (`fastapi-common-packages/SKILL.md` §2) answers *what* to
use for migrations. This is the *how* — three rules for what a migration
file itself has to satisfy to be trustworthy in a year, not just today.

## Migrations must be static

A migration file must not import application code that can change out from
under it — a model class, a service function, a constant defined elsewhere
in the app. If revision `0007` imports `app.modules.products.infra.models`
and that model changes shape in revision `0012`, running `0007` fresh
against a new environment now executes against the *current* model
definition, not the one that existed when `0007` was written — the
migration silently stops doing what its own code appears to say.

The fix: a migration operates on raw table/column definitions via
`op.create_table`, `op.add_column`, `sa.Column(...)`, etc. — never by
importing and using a live ORM model. If a data migration genuinely needs a
model-like structure to iterate rows, define a minimal, frozen one *inline
in the migration file itself*, not imported from the app.

## Migrations must be genuinely reversible

Every migration implements both `upgrade()` and `downgrade()`, and
`downgrade()` actually undoes `upgrade()` — not a `pass` stub. A migration
you can't roll back is a migration you can't safely apply to production,
because the only recovery from a bad deploy is rolling forward with another
fix, under pressure, instead of rolling back.

```python
def upgrade() -> None:
    op.add_column("product", sa.Column("sku", sa.String(50), nullable=True))


def downgrade() -> None:
    op.drop_column("product", "sku")
```

The one case where true reversibility is genuinely impossible is a
destructive data migration (dropping a column that held real data) — for
that, `downgrade()` should at minimum restore the *schema* shape, and the
migration's docstring should say plainly that the data itself isn't
recoverable. Don't skip writing `downgrade()` because it can't be perfect;
write the best one available and say what it doesn't cover.

## File naming: a descriptive slug, in a consistent template

Alembic's default filename is an autogenerated hash plus whatever message
was passed to `alembic revision -m "..."`. Standardize the template so
migrations sort chronologically and are identifiable without opening them:

```
YYYY-MM-DD_<slug>.py
```

```
2026-08-11_add_sku_to_product.py
2026-08-12_create_order_line_table.py
```

Set this in `alembic.ini` so it's enforced by the tool, not by convention
alone:

```ini
file_template = %%(year)d-%%(month).2d-%%(day).2d_%%(slug)s
```

A slug should name *what* the migration does (`add_sku_to_product`), not
restate "migration" or embed a ticket number that means nothing outside
one issue tracker — someone reading `alembic history` should be able to
tell what changed without cross-referencing anything else.
